# Архитектура и техническая спецификация: «Рейс-Проверка»

> Документ фиксирует технические требования, системные ограничения, обоснование стека, архитектуру данных, контракты, эталонный тестовый набор и процесс сборки.

---

## 1. Технические требования и системные ограничения

### 1.1. Назначение и инженерные рамки
- **Stateless In-Memory:** Программа функционирует в изолированном контуре без постоянного хранения клиентских документов. Обработка выполняется исключительно в оперативной памяти.
- **Сброс состояния:** Сессионные данные гарантированно уничтожаются при закрытии программы или сбросе сессии проверки. Локальные базы данных не создаются.

### 1.2. Платформенные ограничения и окружение
- **Поддерживаемые операционные системы:**
  - *Основная платформа:* 64-битные редакции Windows 10 и Windows 11.
  - *Перспективная платформа:* российские дистрибутивы Linux (Astra Linux, РЕД ОС, Альт Линукс) и системы Debian/Ubuntu.
- **Аппаратные ресурсы:**
  - *Процессор:* от 2 физических ядер x86_64, рекомендуется 4 ядра для параллелизации распознавания.
  - *Оперативная память:* от 4 ГБ общего объема. Максимальный порог потребления памяти процессом — не более **1.5 ГБ** даже во время пиковой нагрузки при обработке тяжелых скан-образов.
  - *Лимит размера файла:* не более **50 МБ** на один входящий файл для защиты от исчерпания памяти.
  - *Графический ускоритель:* не требуется. Все вычисления, предобработка изображений и нейросетевой инференс выполняются исключительно силами CPU.
- **Сетевой контур и безопасность по 152-ФЗ:**
  - Локальная обработка: передача содержимого документов, названий контрагентов и персональных данных водителей во внешнюю сеть категорически запрещена.
  - Внешний трафик ограничен редкими легковесными запросами к сервису лицензирования для валидации ключа подписки и проверки обновлений.

### 1.3. Входные и выходные форматы
- **Входные данные:**
  - Загрузка двух файлов через системный диалог операционной системы или перетаскиванием в окно приложения.
  - Поддерживаемые форматы: электронные таблицы XLSX, XLS, CSV, текстовые и графические документы PDF, растровые изображения PNG, JPG, JPEG, файлы Word DOCX, регламентированные XML-титулы электронных накладных ФНС.
- **Выходные данные:**
  - Структурированный объект отчета проверки `SessionReport` в оперативной памяти, передаваемый в интерфейс через сигналы Qt.
  - Четыре стандартизированных статуса каждого проверяемого параметра:
    - `MATCH` (зеленый) — полное совпадение;
    - `CRITICAL` (красный) — критическое несовпадение: номера машин, паспорта, перегруз, несовпадение номеров домов;
    - `WARNING` (желтый) — допустимое несовпадение: различия в организационно-правовых формах, улицах в пределах порога схожести, сокращения;
    - `UNCERTAIN` (серый) — сомнительное считывание с достоверностью ниже 0.70, требующее обязательного визуального контроля оператора.

### 1.4. Эксплуатационные показатели
- **Скорость выполнения:**
  - Структурированные файлы XML, XLSX, CSV, DOCX и текстовый PDF: **1–2 секунды**;
  - Скан-образы и растровые документы с оптическим распознаванием: **8–12 секунд** на 2-ядерном процессоре или **3–5 секунд** на 4-ядерном процессоре.
- **Отзывчивость интерфейса:** Фоновые вычислительные задачи и ввод-вывод вынесены в рабочий поток `QThread`. Главный поток графического интерфейса никогда не блокируется.
- **Формат поставки:** Автономный каталог `--onedir`, упакованный инсталлятором Inno Setup без необходимости установки Python на компьютере пользователя, с установкой в пользовательский профиль `%LOCALAPPDATA%` без прав администратора.

## 3. Архитектура системы и конвейер данных

### 3.1. Схема взаимодействия потоков

```text
               ┌────────────────────────────────────────────────────────┐
               │              ВХОДНЫЕ ФАЙЛЫ (Drag-and-Drop)             │
               │   Заявка (Order)  &  Черновик накладной (Waybill)      │
               └───────────────────────────┬────────────────────────────┘
                                           │
                                           ▼
               ┌────────────────────────────────────────────────────────┐
               │            ГЛАВНЫЙ ПОТОК (PySide6 UI)                  │
               │   • Зона приема файлов    • Таблица расхождений QSS    │
               └─────────────┬────────────────────────────▲─────────────┘
      Сигнал запуска анализа │                            │ Сигнал: SessionReport
                             ▼                            │
┌─────────────────────────────────────────────────────────┴─────────────┐
│                 ФОНОВЫЙ ВЫЧИСЛИТЕЛЬНЫЙ ПОТОК (QThread)                 │
│                                                                        │
│ 1. [Маршрутизация и извлечение сырого текста / ячеек]                  │
│    ├── Цифровые файлы: XML, XLSX, XLS, CSV, DOCX, текстовый PDF       │
│    └── Сканы / Графика: pypdfium2 ──> OpenCV ──> RapidOCR (ONNX)       │
│                                                                        │
│ 2. [Семантический парсер (Information Extraction)]                    │
│    └── Поиск якорных маркеров и извлечение сущностей в DocumentPackage │
│                                                                        │
│ 3. [Нормализация реквизитов]                                          │
│    ├── Госномера: маска ГОСТ + кириллизация + исправление OCR-ошибок   │
│    ├── Вес груза: приведение к кг (числовые значения, тонны * 1000)   │
│    └── Адреса: изоляция географии от номеров домов и строений         │
│                                                                        │
│ 4. [Движок сопоставления и бизнес-правил]                             │
│    ├── Строгая сверка: госномера, паспорта, номера домов              │
│    ├── Нечеткое сравнение: улицы, города, ФИО (rapidfuzz)              │
│    ├── Контроль массы: масса_груза_кг <= грузоподъемность_тс_кг        │
│    └── Контроль достоверности OCR: confidence < 0.70 => UNCERTAIN     │
│                                                                        │
│ 5. [Сборка отчета]                                                    │
│    └── Генерация итогового SessionReport и отправка сигнала в UI       │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.2. Шаги конвейера обработки данных

1. **Прием и валидация файлов:** Проверка расширений, прав доступа и отсечение файлов размером более 50 МБ.
2. **Маршрутизация парсинга:**
   - Структурированные файлы разбираются прямыми парсерами с извлечением текста и ячеек.
   - Скан-образы и растровые документы конвертируются через `pypdfium2`, предобрабатываются в OpenCV и передаются в `RapidOCR`.
3. **Семантическое извлечение сущностей:** Поиск маркеров реквизитов по словарям синонимов и шаблонам с привязкой смежных значений по координатам блоков или колонкам таблиц.
4. **Нормализация параметров:**
   - *Госномера ТС и прицепов:* транслитерация визуально схожих букв латиницы в кириллицу; коррекция ошибок оптического распознавания по ГОСТ-маске.
   - *Масса груза:* парсинг дробных чисел с разделителями точкой и запятой; при маркерах тонн значение умножается на 1000 и приводится к целым килограммам. Числа от 1 до 50 в контексте веса трактуются как тонны.
   - *Паспорта и телефоны:* удаление служебных разделителей, валидация 10 цифр паспорта РФ, приведение телефонов к стандарту `+7XXXXXXXXXX`.
   - *Адреса:* разбиение строки на географическую часть (город, улица) и строгие идентификаторы (номера домов, корпусов, строений).
5. **Сопоставление и применение бизнес-правил:**
   - Строгая посимвольная сверка номеров машин, паспортов, номеров домов и строений. Любое несовпадение приводит к критическому статусу `CRITICAL`.
   - Нечеткое сопоставление наименований и улиц через `rapidfuzz`: при сходстве от 85% — статус `MATCH`, от 60% до 84% — предупреждение `WARNING`, менее 60% — критическая ошибка `CRITICAL`.
   - Контроль перегруза: масса груза не должна превышать заявленную грузоподъемность автомобиля.
   - Контроль достоверности распознавания: при уверенности любого поля ниже 0.70 строке присваивается статус сомнительного считывания `UNCERTAIN`.
6. **Трансляция результатов:** Упаковка результатов в объект `SessionReport` и передача в главный поток интерфейса через сигнал Qt.

## 4. Контракты данных

Все модули приложения изолированы друг от друга и взаимодействуют исключительно через типизированные структуры данных, определенные в [`src/freight_check/contracts.py`](../src/freight_check/contracts.py):

1. **`ValidationStatus`** — строковое перечисление статусов проверки параметра:
   - `MATCH` — подтвержденное совпадение (зеленый цвет);
   - `CRITICAL` — блокирующее расхождение: ошибка в госномере, паспорте, адресе или перегруз (красный цвет);
   - `WARNING` — допустимое расхождение в наименовании или адресе в пределах допустимого порога схожести (желтый цвет);
   - `UNCERTAIN` — сомнительное считывание с достоверностью распознавания ниже 0.70, требующее проверки человеком (серый цвет).
2. **`ExtractedField`** — атомарная модель распознанного поля документа. Содержит исходную строку (`raw_value`), нормализованное значение (`normalized_value`), показатель уверенности (`confidence`) и координаты блока на странице (`source_box`).
3. **`DocumentPackage`** — контейнер разобранного документа. Фиксирует роль документа (`order` или `waybill`), путь к исходному файлу, структурированный набор извлеченных параметров перевозки (автомобиль, прицеп, водитель, масса, объем, пункты маршрута, спецтребования) и список возникших при парсинге ошибок.
4. **`ValidationRow`** — строка результата сопоставления конкретного параметра. Содержит наименование параметра, значение из заявки, значение из накладной, итоговый статус проверки и понятное оператору текстовое объяснение.
5. **`SessionReport`** — итоговый отчет сессии валидации. Включает общий статус сессии, количество критических ошибок, количество предупреждений, время обработки в миллисекундах и список строк `ValidationRow` для отображения в таблице расхождений.

## 5. Распределение обязанностей и план реализации

### 5.1. Матрица обязанностей

| Роль | Зона ответственности | Ключевые задачи |
| :--- | :--- | :--- |
| **Разработчик 1** | Интерфейс, асинхронность и сборка | Разработка экрана загрузки и таблицы расхождений со статусами на PySide6; организация потока `QThread`; скрипты упаковки PyInstaller и Inno Setup; тесты интерфейса. |
| **Разработчик 2** | Парсинг файлов и конвейер OCR | Реализация парсеров XML, XLSX, XLS, CSV, DOCX, PDF; графический конвейер растеризации и предобработки в OpenCV; инференс RapidOCR; тесты парсинга. |
| **Разработчик 3** | Семантика, нормализация и сопоставление | Извлечение параметров по якорным маркерам; алгоритмы нормализации госномеров, веса и адресов; движок сопоставления и бизнес-правил; сборка `SessionReport`; тесты логики. |

### 5.2. Этапы реализации
1. **Этап 1: Фиксация контрактов данных.** Закрепление моделей обмена и базового тестового окружения.
2. **Этап 2: Параллельная разработка компонентов.** Разработка интерфейса с моковыми данными, создание парсеров и графического пайплайна, реализация семантического извлечения и нормализации.
3. **Этап 3: Сквозная интеграция.** Объединение модулей в фоновый конвейер, калибровка порогов схожести строк и уверенности распознавания на эталонных данных.
4. **Этап 4: Профилирование и сборка.** Контроль лимита памяти до 1.5 ГБ, упаковка инсталлятора под Windows, тестирование на чистых машинах.

## 6. Стратегия тестирования и контроль качества

### 6.1. Уровни тестирования
- **Модульное тестирование:**
  - Проверка парсеров всех форматов входных файлов;
  - Тестирование нормализации веса и госномеров по ГОСТ-маске;
  - Тестирование раздельного сравнения адресов с посимвольной проверкой номеров домов;
  - Тестирование математического условия перегруза.
- **Интеграционное тестирование:**
  - Консольный прогон сквозного конвейера обработки пары документов без графической оболочки;
  - Замер времени обработки файлов.
- **Системное тестирование:**
  - Проверка утечек памяти: последовательная обработка 30 пар документов с контролем потолка потребления памяти процессом до 1.5 ГБ;
  - Проверка сетевой безопасности: полный запрет исходящего сетевого трафика при обработке документов.

### 6.2. Эталонный тестовый набор из 15 пар документов

| № | Сценарий | Количество пар | Описание тест-кейса | Ожидаемый результат |
| :---: | :--- | :---: | :--- | :--- |
| 1 | **Корректный рейс** | 3 пары | Полное совпадение всех проверяемых полей | Все строки со статусом `MATCH` |
| 2 | **Критический перегруз** | 3 пары | Заявленный вес груза превышает грузоподъемность машины | Строка со статусом `CRITICAL` с указанием величины перегруза |
| 3 | **Опечатки в идентификаторах** | 3 пары | Ошибки в госномерах, паспортах или номерах домов | Статус `CRITICAL` по соответствующим строкам |
| 4 | **Допустимые расхождения** | 3 пары | Разный порядок слов в юрлицах, сокращения улиц и городов | Статус `WARNING` при сходстве от 60% |
| 5 | **Низкокачественные сканы** | 3 пары | Размытые или зашумленные скан-образы | Статус `UNCERTAIN` для полей с уверенностью ниже 0.70 |

### 6.3. Критерии приемки
- Выявление не менее 95% критических расхождений на эталонном наборе;
- Время обработки цифровых пар файлов — до 1–2 секунд, скан-образов — до 8–12 секунд на 2-ядерном процессоре;
- Устойчивость приложения при подаче поврежденных или некорректных файлов;
- Автономный запуск дистрибутива на чистой системе Windows без прав администратора.

## 7. Процесс сборки и дистрибуции

### 7.1. Спецификация сборщика PyInstaller (`freight_check.spec`)
- **Режим поставки:** Строго каталог `--onedir`. Сборка в один файл запрещена для исключения задержек распаковки (15–20 с) в каталог `%TEMP%` при каждом запуске.
- **Оконный режим:** `--noconsole` / `--windowed` (отключение консольного окна Windows).
- **Включение ресурсов:**
  - `assets/icons/` — иконки приложения (.ico, .svg, .png);
  - `assets/styles/` — стили QSS и векторные элементы интерфейса;
  - `assets/models/` — каталог моделей нейросетей RapidOCR.
- **Оптимизация размера:** Принудительное исключение более 40 неиспользуемых компонентов Qt (QtQuick, QtQml, QtWebEngine, Qt3D, QtMultimedia, QtSensors и др.), сократившее размер дистрибутива с 650 МБ до 330 МБ на диске.

### 7.2. Инсталлятор Inno Setup (`installer.iss`)
- **Целевая платформа:** Windows 10/11 (x64 only).
- **Права доступа:** Строго без прав администратора (`PrivilegesRequired=lowest`).
- **Каталог установки:** Профиль текущего пользователя `%LOCALAPPDATA%\Programs\FreightCheck` (`{autopf}\FreightCheck`).
- **Ярлыки:** Меню «Пуск» (`{group}`) и опциональный ярлык на Рабочем столе (`{autodesktop}`).
- **Очистка данных:** Директива `[UninstallDelete]` для полного удаления временных кэшей в `%LOCALAPPDATA%\FreightCheck` и `%TEMP%`.

### 7.3. Автоматизация сборки и CI/CD
- **Локальная оркестрация:**
  - `build.ps1` — запуск сборщика с параметрами `-SkipTests`, `-NoInstaller`, `-Clean`.
  - `scripts/build.py` — кроссплатформенный скрипт сквозного конвейера: `uv sync` ──> линтер/тесты ──> сборка каталога PyInstaller ──> компиляция Inno Setup ──> валидация целостности артефактов.
- **GitHub Actions Workflow (`.github/workflows/build-and-distribute.yml`):**
  - Запуск на виртуальной машине `windows-latest`;
  - Настройка `uv` с кэшированием и Python 3.13;
  - Установка Inno Setup через `choco install innosetup --no-progress`;
  - Запуск полного конвейера `uv run python scripts/build.py`;
  - Публикация артефактов: портативный архив `freight-check-portable-windows-x64.zip` и инсталлятор `freight-check-setup-v*.exe`.
