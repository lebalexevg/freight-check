## 1. Обзор проекта и миссия

### 1.1. Суть продукта
**«Рейс-Проверка» (`freight-check`)** — автономная десктопная утилита для логистов и диспетчеров малого и среднего автотранспортного бизнеса (МСП) в РФ.
Программа выполняет автоматическую локальную кросс-валидацию (диффчекер) между входящей клиентской заявкой на перевозку и черновиком электронной транспортной накладной (ЭТрН) до выпуска автомобиля в рейс и передачи документов в государственную информационную систему электронных перевозочных документов (ГИС ЭПД).

### 1.2. Проблема и бизнес-контекст
* **Нормативные требования:** Федеральный закон № 140-ФЗ и обязательное внедрение ЭТрН. Любые опечатки и расхождения мгновенно фиксируются контролирующими органами (ФНС, Ространснадзор).
* **Цена ошибки:** Простой автотранспорта, срыв сроков доставки, штрафы от заказчиков, отказ ФНС в признании расходов по налогу на прибыль и вычетов по НДС.
* **Кадровый фактор:** Диспетчеры тратят 10–15 минут на ручную сверку одного рейса в стрессовых условиях. «Рейс-Проверка» выступает «второй парой глаз», сокращая цикл валидации до 1 минуты.

### 1.3. Границы продукта (Scope & Non-Scope)
| Входит в объем (In-Scope) | Категорически НЕ входит (Non-Scope) |
| :------------------------- | :----------------------------------- |
| Прием разнородных форматов: PDF (текст/сканы), Excel (XLSX, XLS), CSV, Word (DOCX), XML титулов ЭТрН, изображения (PNG, JPG). | Прямая отправка документов в ГИС ЭПД или ФНС (зона ответственности операторов ЭДО). |
| Автоматическое извлечение реквизитов без предварительной ручной разметки документов. | Подписание файлов усиленной квалифицированной электронной подписью (УКЭП). |
| Нормализация форматов (госномера, масса, адреса) и эвристическое/нечеткое сопоставление полей. | Замена ERP/TMS систем (1С, МойСклад) или личных кабинетов операторов ЭДО (СБИС, Диадок). |
| Формирование локального отчета расхождений по категориям (совпадение, критическая ошибка, предупреждение, сомнительное считывание). | Модификация исходных файлов пользователя без его прямого подтверждения. |
| 100% локальная обработка данных в оперативной памяти компьютера. | Передача персональных данных или содержимого документов во внешнюю сеть. |

## 2. Архитектурные инварианты и системные ограничения

Каждый ИИ-агент обязан строго соблюдать следующие инженерные правила:

1. **Безопасность данных и 152-ФЗ (Strict Offline Processing):**
   * Обработка документов, извлечение текста, OCR и сопоставление выполняются **строго локально в ОЗУ**.
   * Запрещена отправка фрагментов документов, ФИО водителей, номеров и адресов во внешние API или телеметрию.
   * Допустимы только легковесные HTTPS-запросы валидации ключа лицензии и проверки обновлений версий.
2. **Отсутствие постоянного хранения (Stateless In-Memory):**
   * Никаких локальных баз данных (SQLite и др.) для хранения содержимого документов.
   * Все промежуточные структуры уничтожаются при сбросе сессии или закрытии приложения.
3. **Ограничения по ресурсам:**
   * **Потолок RAM:** пиковое потребление памяти процессом не должно превышать **1.5 ГБ** даже во время интенсивного OCR.
   * **Размер входящих файлов:** жесткий лимит — не более **50 МБ** на файл (защита от OOM).
   * **Вычисления на CPU:** использование легковесных моделей (`rapidocr-onnxruntime`), инференс исключительно на CPU без требований к GPU.
4. **Асинхронность UI (PySide6):**
   * Главный поток (Main Thread / GUI) **никогда** не выполняет ввод-вывод, парсинг, OCR или матчинг.
   * Все тяжелые задачи выносятся в фоновый поток (`QThread` / `Worker`), взаимодействующий с GUI исключительно через потокобезопасные сигналы и слоты Qt.
5. **Целевые KPI производительности:**
   * Цифровые документы (XML, XLSX, текстовый PDF, DOCX): сопоставление за **1–2 секунды**.
   * Скан-образы и растровые документы (с OCR): **8–12 секунд** (на 2-ядерном CPU) или **3–5 секунд** (на 4-ядерном CPU).
   * Точность выявления критических расхождений: не менее **95%**.

## 4. Контракты данных (`contracts.py`) — Single Source of Truth

Слои системы строго изолированы. Обмен данными происходит **только** через модели данных из `src/freight_check/contracts.py`:

* **`ValidationStatus(StrEnum)`**:
  * `MATCH` (зеленый) — полное совпадение реквизита.
  * `CRITICAL` (красный) — критическое несовпадение (госномера, паспорта, перегруз, несовпадение номеров домов).
  * `WARNING` (желтый) — допустимое несовпадение (незначительные различия в наименованиях компаний, улицах, сокращения).
  * `UNCERTAIN` (серый) — сомнительное считывание (`confidence < 0.70`), обязателен ручной контроль оператора.
* **`ExtractedField`** (`frozen=True, slots=True`):
  * `raw_value: str` — исходная строка из документа.
  * `normalized_value: str` — нормализованное значение.
  * `confidence: float` — достоверность (1.0 для структурированных файлов, 0.0–1.0 для OCR).
  * `source_box: tuple[int, int, int, int] | None` — экранные/страничные координаты `(x, y, w, h)`.
* **`DocumentPackage`** (`slots=True`):
  * `document_role: str` — `"order"` (заявка) или `"waybill"` (накладная).
  * `file_path: str` — путь к файлу.
  * Поля реквизитов (`truck_number`, `trailer_number`, `truck_capacity_kg`, `driver_name`, `driver_passport`, `driver_phone`, `cargo_weight_kg`, `cargo_volume_m3`, `cargo_places_count`, `loading_point`, `unloading_point`, `temperature_conditions`, `special_instructions`).
  * `parsing_errors: list[str]` — ошибки, возникшие при разборе файла.
* **`ValidationRow`** (`frozen=True, slots=True`):
  * Атомарная строка таблицы расхождений: `parameter_name`, `order_value`, `waybill_value`, `status`, `explanation`.
* **`SessionReport`** (`slots=True`):
  * Итоговый отчет: `overall_status`, `critical_errors_count`, `warnings_count`, `processing_time_ms`, `rows: list[ValidationRow]`.

> **Важно для агентов:** Не модифицируйте поля и сигнатуры `contracts.py` без согласования архитектурных изменений со всеми зависимыми модулями.

## 5. Распределение обязанностей и модульная структура

Архитектура рассчитана на 3 специализированных направления (роли разработчиков / агентов):

```text
src/freight_check/
├── contracts.py          # Контракты данных (базовый слой)
├── ui/                   # [Роль 1: UI, асинхронность и сборка]
│   ├── main_window.py    # Главное окно (Drag-and-Drop, панель действий)
│   ├── diff_table.py     # Таблица расхождений со стилизацией QSS
│   └── worker.py         # QThread для фонового конвейера
├── parsers/              # [Роль 2: Парсинг файлов и OCR]
│   ├── router.py         # Маршрутизатор по типам файлов и расширениям
│   ├── direct_parsers.py # Чтение XML (ЭТрН), XLSX, XLS, CSV, DOCX, текстового PDF
│   └── ocr_pipeline.py   # pypdfium2 (растеризация) + OpenCV + RapidOCR
└── core/                 # [Роль 3: Семантика, нормализация и сопоставление]
    ├── extract.py        # Привязка якорных слов и заполнение DocumentPackage
    ├── normalize.py      # ГОСТ-номера, вес (кг), очистка телефонов/паспортов, адреса
    └── matcher.py        # rapidfuzz, строгая сверка, контроль веса, сборка SessionReport
```

### 5.1. Роль 1: UI, асинхронность и сборка (`ui/` + packaging)
* **Зона ответственности:** Визуальная часть на PySide6, отзывчивость UI, фоновые потоки, дистрибуция.
* **Ключевые файлы:** `src/freight_check/ui/`, сборка PyInstaller и Inno Setup.
* **Правила:**
  * Никаких блокирующих операций в основном потоке.
  * Стилизация таблицы расхождений через QSS с четкой цветовой индикацией статусов (`MATCH` — зеленый, `CRITICAL` — красный, `WARNING` — желтый, `UNCERTAIN` — серый).
  * Инсталлятор Windows: сборка PyInstaller в каталог (`--onedir`), включение каталогов `assets/models/` и `assets/styles/`, упаковка через Inno Setup для установки в `%LOCALAPPDATA%` без прав администратора.

### 5.2. Роль 2: Парсинг файлов и конвейер OCR (`parsers/`)
* **Зона ответственности:** Чтение структурированных файлов и извлечение сырого текста со скан-образов.
* **Ключевые файлы:** `src/freight_check/parsers/`, каталог моделей `assets/models/`.
* **Правила:**
  * Для XML ЭТрН: использование встроенного `xml.etree.ElementTree` (парсинг регламентированных титулов ФНС).
  * Для таблиц: `openpyxl` (XLSX), `xlrd` (XLS), `csv`.
  * Для текстовых документов: `python-docx` (DOCX), `pdfplumber` (цифровой PDF с координатами).
  * Для скан-образов: `pypdfium2` -> `opencv-python-headless` (бинаризация, дескью, контраст) -> `rapidocr-onnxruntime`.
  * Веса ONNX хранятся локально в `assets/models/` (вес не более 30 МБ, работа строго на CPU).
  * Возврат сырых текстовых блоков с координатами и показателем `confidence`.

### 5.3. Роль 3: Семантика, нормализация и сопоставление (`core/`)
* **Зона ответственности:** Понимание смысла реквизитов, нормализация и движок бизнес-правил.
* **Ключевые файлы:** `src/freight_check/core/`.
* **Правила:** Реализация специализированных алгоритмов сопоставления (см. раздел 6).

## 6. Бизнес-правила сопоставления и нормализации

Агенты, работающие над модулем `core/`, обязаны руководствоваться следующими алгоритмическими правилами:

### 6.1. Автомобильные номера ТС и прицепов
1. **Транслитерация латиницы:** Буквы, визуально совпадающие с латиницей (`A, B, E, K, M, H, O, P, C, T, Y, X`), принудительно приводятся к кириллице (`А, В, Е, К, М, Н, О, Р, С, Т, У, Х`).
2. **Исправление типичных ошибок OCR по ГОСТ-маске:**
   * Стандартный номер ТС: `[Буква][3 Цифры][2 Буквы][2-3 Цифры региона]`.
   * На позициях цифр: заменять `О -> 0`, `В -> 8`, `З -> 3`.
   * На позициях букв: заменять `0 -> О`, `8 -> В`, `3 -> З`.
3. **Сравнение:** **Строго посимвольное**. Любое расхождение (даже в одном символе) — статус `CRITICAL`.

### 6.2. Масса груза и грузоподъемность автомобиля
1. **Нормализация веса:**
   * Поддержка разделителей: точка и запятая (`1,5` -> `1.5`).
   * При обнаружении маркеров «т», «тн», «тонн», «t» число умножается на 1000 и приводится к целому числу килограммов.
   * Чистые числа от 1 до 50 при контексте веса трактовать как тонны (`20` -> `20 000 кг`).
2. **Контроль перегруза (бизнес-инвариант):**
   * Если известна грузоподъемность автомобиля (`truck_capacity_kg`):
     $$\text{cargo\_weight\_kg} \le \text{truck\_capacity\_kg}$$
   * Если масса груза превышает грузоподъемность — генерируется строка со статусом `CRITICAL` и пояснением: *«Превышение грузоподъемности машины на X кг!»*.
3. **Сверка массы между документами:**
   * Несовпадение массы груза в заявке и накладной более чем на допустимый технологический допуск (по умолчанию 0 кг для тарного груза) — статус `CRITICAL`.

### 6.3. Адреса погрузки и выгрузки
Строка адреса разделяется на две логические части:
1. **Географическая часть (населенный пункт, улица, проспект):**
   * Сравнивается через нечеткий поиск `rapidfuzz.fuzz.token_set_ratio`.
   * Сходство $\ge 85\%$ — `MATCH`.
   * Сходство от $60\%$ до $85\%$ — `WARNING` (сокращения «г.», «ул.», перестановка слов).
   * Сходство $< 60\%$ — `CRITICAL`.
2. **Идентификаторы строений (номера домов, корпусов, строений, боксов, ворот):**
   * Извлекаются регулярными выражениями.
   * Проверяются **строго посимвольно**. Несовпадение номера дома (например, заявка: д. 15, накладная: д. 51) — **всегда** статус `CRITICAL`.

### 6.4. Паспортные данные и контакты водителя
* Серия и номер паспорта очищаются от пробелов и дефисов -> строгая посимвольная сверка (10 цифр). Несовпадение — `CRITICAL`.
* ФИО водителя нормализуется (удаление лишних пробелов, капитализация). Нечеткое сравнение: при опечатке в 1 символ — `WARNING`, несовпадение фамилии — `CRITICAL`.
* Телефон нормализуется к формату `+7XXXXXXXXXX`.

### 6.5. Контроль достоверности распознавания (OCR Confidence)
* Если при оптическом распознавании уверенность поля `confidence < 0.70`, соответствующей строке присваивается статус `UNCERTAIN` (серый цвет) независимо от текстового совпадения. Оператор должен визуально перепроверить это поле.

## 7. Стандарты кода, линтинг и контроль типов

* **Статический анализатор типов:** `basedpyright` в режиме `typeCheckingMode = "standard"`.
  * 100% аннотация типов всех параметров функций и возвращаемых значений.
  * Никаких нетипизированных `def foo(...)`.
  * Использование стандартных дженериков Python 3.13 (`list[str]`, `dict[str, Any]`, `X | None`).
* **Тестирование:** `pytest`.
* **Хуки перед коммитом:** `pre-commit` (trailing-whitespace, end-of-file-fixer, check-yaml, ruff, basedpyright, pytest).

## 8. Git-регламент и соглашения о коммитах

1. **Ветка `main` священна:** Прямые коммиты в `main` категорически запрещены.
2. **Ветки задач:** Вся разработка ведется в ветках `feature/<краткое-название>` или `bugfix/<краткое-название>`.
3. **Формат коммитов (Conventional Commits):**
   ```text
   <тип>(<область>): <описание с маленькой буквы в повелительном наклонении>
   ```
   * **Типы:** `feat`, `fix`, `test`, `refactor`, `perf`, `chore`, `ci`, `docs`.
   * **Разрешенные области (`scope`):**
     * `contracts` — модели данных и перечисления (`contracts.py`)
     * `ui` — PySide6 экраны, виджеты, стили QSS
     * `parsers` — прямое чтение файлов (XML, Excel, DOCX, PDF)
     * `ocr` — конвейер растеризации и распознавания изображений
     * `extract` — извлечение сущностей и поиск якорных маркеров
     * `norm` — алгоритмы нормализации (госномера, вес, адреса)
     * `matcher` — движок сопоставления и бизнес-правил
     * `pack` — сборка дистрибутива (PyInstaller, Inno Setup)
     * `infra` — настройки CI, uv, pre-commit, pyproject.toml

*Примеры:*
* `feat(extract): реализовать поиск якорных маркеров грузополучателя`
* `fix(norm): исправить обработку запятой в дробном весе груза`
* `test(matcher): добавить тесты для проверки перегруза автомобиля`

## 9. Эталонный тестовый набор (15 пар документов)

При реализации и валидации конвейера ориентироваться на следующие 5 эталонных сценариев:

| № | Сценарий | Кол-во пар | Описание тест-кейса | Ожидаемый результат |
| :- | :------- | :--------: | :------------------ | :------------------ |
| 1 | **Корректный рейс** | 3 пары | Полное совпадение всех реквизитов | 100% строк со статусом `MATCH` (зеленый) |
| 2 | **Критический перегруз** | 3 пары | Заявленный вес груза превышает грузоподъемность ТС | Строка со статусом `CRITICAL` (красный) с описанием превышения |
| 3 | **Опечатки в идентификаторах** | 3 пары | Ошибки в госномерах, паспортах или номерах домов | Статус `CRITICAL` по соответствующим строкам |
| 4 | **Допустимые расхождения** | 3 пары | Разный порядок слов в юрлицах, сокращения («г.», «ул.») | Статус `WARNING` (желтый) при сходстве $\ge 60\%$ |
| 5 | **Низкокачественные сканы** | 3 пары | Размытые, смазанные или зашумленные сканы/фото | Статус `UNCERTAIN` (серый) для полей с confidence $< 0.70$ |

## 10. Памятка команд для ИИ-агентов (CLI Cheat Sheet)

Все команды запускаются в корне репозитория через `uv run`:

```bash
# 1. Запуск всех тестов
uv run pytest

# 2. Запуск тестов с подробным выводом
uv run pytest -v

# 3. Статическая проверка типов (basedpyright)
uv run basedpyright

# 4. Проверка линтером Ruff
uv run ruff check

# 5. Автоматическое исправление ошибок Ruff
uv run ruff check --fix

# 6. Форматирование кода через Ruff
uv run ruff format

# 7. Комплексный прогон всех проверок pre-commit
uv run pre-commit run --all-files

# 8. Запуск приложения в режиме разработки
uv run freight-check
```

## 11. Чек-лист ИИ-агента перед сдачей задачи

Перед тем как сообщить пользователю о завершении задачи или подготовить коммит, агент обязан:

- [ ] **1. Запустить тесты:** `uv run pytest` завершается без единой ошибки.
- [ ] **2. Проверить типы:** `uv run basedpyright` выдает `0 errors, 0 warnings, 0 notes`.
- [ ] **3. Проверить стиль:** `uv run ruff check` и `uv run ruff format` не находят нарушений.
- [ ] **4. Проверить целостность контрактов:** Никаких сломанных зависимостей между `contracts.py`, `ui`, `parsers` и `core`.
- [ ] **5. Проверить локальность:** Код не содержит сетевых обращений с данными документов и не создает постоянных локальных баз данных.
- [ ] **6. Проверить сообщение коммита:** Сообщение соответствует соглашению Conventional Commits с валидным типом и scope.
