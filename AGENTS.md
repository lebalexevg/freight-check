## 2. Архитектурные инварианты и системные ограничения

Каждый ИИ-агент обязан строго соблюдать следующие инженерные правила:

1. **Безопасность данных и 152-ФЗ:**
   * Обработка документов, извлечение текста, оптическое распознавание и сопоставление выполняются **строго локально в оперативной памяти**.
   * Запрещена отправка содержимого документов, фрагментов текста, ФИО водителей, номеров и адресов во внешнюю сеть, сторонние API или телеметрию.
   * Допустимы только легковесные HTTPS-запросы валидации ключа лицензии и проверки обновлений версий.
2. **Отсутствие постоянного хранения (Stateless In-Memory):**
   * Никаких локальных баз данных для хранения содержимого документов.
   * Все промежуточные структуры уничтожаются при сбросе сессии или закрытии приложения.
3. **Ограничения по ресурсам:**
   * **Потолок памяти:** пиковое потребление памяти процессом не должно превышать **1.5 ГБ** даже во время оптического распознавания скан-образов.
   * **Размер входящих файлов:** не более **50 МБ** на файл для защиты от исчерпания памяти.
   * **Вычисления на CPU:** использование легковесных моделей `rapidocr-onnxruntime`, инференс исключительно на процессоре без требований к GPU.
4. **Асинхронность интерфейса:**
   * Главный поток интерфейса **никогда** не выполняет ввод-вывод, парсинг, распознавание или сопоставление.
   * Все тяжелые задачи выносятся в фоновый поток `QThread`, взаимодействующий с интерфейсом исключительно через потокобезопасные сигналы и слоты Qt.
5. **Целевые показатели производительности:**
   * Структурированные файлы XML, Excel, Word и текстовый PDF: сопоставление за **1–2 секунды**.
   * Скан-образы и растровые документы с оптическим распознаванием: **8–12 секунд** на 2-ядерном процессоре или **3–5 секунд** на 4-ядерном процессоре.
   * Точность выявления критических расхождений: не менее **95%**.

## 3. Бизнес-правила сопоставления и нормализации

При работе над семантическим извлечением, нормализацией и движком сопоставления в `src/freight_check/core/` агент руководствуется следующими алгоритмическими правилами:

### 3.1. Автомобильные номера машин и прицепов
1. **Транслитерация латиницы:** Буквы, визуально совпадающие с латиницей (`A, B, E, K, M, H, O, P, C, T, Y, X`), принудительно приводятся к кириллице (`А, В, Е, К, М, Н, О, Р, С, Т, У, Х`).
2. **Исправление типичных ошибок распознавания по ГОСТ-маске:**
   * Стандартный номер ТС: буква, 3 цифры, 2 буквы, 2 или 3 цифры региона.
   * На позициях цифр заменять `О -> 0`, `В -> 8`, `З -> 3`.
   * На позициях букв заменять `0 -> О`, `8 -> В`, `3 -> З`.
3. **Сравнение:** Строго посимвольное. Любое расхождение даже в одном символе — статус `CRITICAL`.

### 3.2. Масса груза и грузоподъемность автомобиля
1. **Нормализация веса:**
   * Поддержка разделителей: точка и запятая.
   * При обнаружении маркеров «т», «тн», «тонн» число умножается на 1000 и приводится к целому числу килограммов.
   * Числа от 1 до 50 при контексте веса трактовать как тонны (`20` -> `20 000 кг`).
2. **Контроль перегруза:**
   * Если известна грузоподъемность автомобиля `truck_capacity_kg`:
     `cargo_weight_kg <= truck_capacity_kg`
   * Если масса груза превышает грузоподъемность, генерируется строка со статусом `CRITICAL` и пояснением: *«Превышение грузоподъемности машины на X кг!»*.
3. **Сверка массы между документами:**
   * Несовпадение массы груза в заявке и накладной более чем на технологический допуск — статус `CRITICAL`.

### 3.3. Адреса погрузки и выгрузки
Строка адреса разделяется на две логические части:
1. **Географическая часть (населенный пункт, улица, проспект):**
   * Сравнивается через нечеткий поиск `rapidfuzz.fuzz.token_set_ratio`.
   * Сходство от 85% — `MATCH`.
   * Сходство от 60% до 84% — `WARNING`: допустимые сокращения «г.», «ул.» или перестановка слов.
   * Сходство менее 60% — `CRITICAL`.
2. **Идентификаторы строений (номера домов, корпусов, строений):**
   * Извлекаются регулярными выражениями.
   * Проверяются строго посимвольно. Несовпадение номера дома — всегда статус `CRITICAL`.

### 3.4. Паспортные данные и контакты водителя
* Серия и номер паспорта очищаются от пробелов и дефисов, после чего выполняется строгая посимвольная сверка 10 цифр. Несовпадение — `CRITICAL`.
* ФИО водителя нормализуется. Нечеткое сравнение: при опечатке в 1 символ — `WARNING`, несовпадение фамилии — `CRITICAL`.
* Телефон нормализуется к формату `+7XXXXXXXXXX`.

### 3.5. Контроль достоверности распознавания
* Если при распознавании уверенность поля `confidence < 0.70`, соответствующей строке присваивается статус `UNCERTAIN` независимо от текстового совпадения. Оператор должен визуально перепроверить это поле.

## 4. Регламент Git, команды и стандарты разработки

Вся инженерная деятельность агента строго следует правилам из руководства разработчика:

1. **Ветки и сообщения коммитов:**
   * Прямые коммиты в `main` категорически запрещены.
   * Вся разработка ведется в ветках `feature/<название>` или `bugfix/<название>`.
   * Сообщения коммитов формируются строго по Conventional Commits с валидным типом и обязательной областью (`scope`): `contracts`, `ui`, `parsers`, `ocr`, `extract`, `norm`, `matcher`, `pack`, `infra`.
   * Полные правила и примеры см. в [`docs/contributing.md#3-регламент-работы-с-git`](docs/contributing.md#3-регламент-работы-с-git) и [`docs/contributing.md#4-соглашения-о-коммитах`](docs/contributing.md#4-соглашения-о-коммитах).
2. **Инструменты контроля качества и запуск команд:**
   * **Два поддерживаемых способа работы:**
     - **Через `mise` (рекомендуется при наличии `mise` в системе):** запуск задач через `mise run <task>` (`mise run check`, `mise run test`, `mise run lint`, `mise run typecheck`, `mise run format`) либо вызовы через `mise exec -- uv run ...`. Это гарантирует использование фиксированных версий Python 3.13 и uv из `mise.toml`.
     - **Нативно через `uv`:** при отсутствии `mise` все команды выполняются напрямую через `uv run` (`uv run pytest`, `uv run basedpyright`, `uv run ruff check`).
   * Список команд и стандарты кода см. в [`docs/contributing.md#2-команды-разработки-и-контроля-качества`](docs/contributing.md#2-команды-разработки-и-контроля-качества) и [`docs/contributing.md#5-стандарты-кода-и-линтинг`](docs/contributing.md#5-стандарты-кода-и-линтинг).
3. **Эталонные тестовые сценарии:**
   * Для проверки конвейера сопоставления агент использует эталонный набор из 15 пар документов по 5 сценариям, описанным в [`docs/architecture.md#62-эталонный-тестовый-набор-из-15-пар-документов`](docs/architecture.md#62-эталонный-тестовый-набор-из-15-пар-документов).

## 5. Чек-лист ИИ-агента перед сдачей задачи

Перед тем как сообщить пользователю о завершении задачи или подготовить коммит, агент обязан:

- [ ] **1. Запустить тесты:** `mise run test` (или `uv run pytest`) завершается без единой ошибки.
- [ ] **2. Проверить типы:** `mise run typecheck` (или `uv run basedpyright`) выдает `0 errors, 0 warnings, 0 notes`.
- [ ] **3. Проверить стиль:** `mise run lint` и `mise run format` (или `uv run ruff check` и `uv run ruff format`) не находят нарушений.
- [ ] **4. Комплексная проверка (при наличии mise):** `mise run check` успешно проходит все проверки за один вызов.
- [ ] **5. Проверить целостность контрактов:** Никаких сломанных зависимостей между `contracts.py`, `ui`, `parsers` и `core`.
- [ ] **6. Проверить локальность:** Код не содержит сетевых обращений с данными документов и не создает постоянных локальных баз данных.
- [ ] **7. Проверить ветку и сообщение коммита:** Работа ведется в ветке `feature/*` или `bugfix/*`, а сообщение коммита строго соответствует соглашению Conventional Commits со scope из [`docs/contributing.md`](docs/contributing.md).
